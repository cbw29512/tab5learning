# Test device enrollment and mutual authentication

## State and data
- Existing planned assignment remains PLANNED.
- Test-only credential record: normalized device_id (unique, must have a planned assignment), random 32-byte shared secret, created_at UTC, actor (authorized admin), state KEY_PENDING. The local test database is outside Git, never returned to browser or logs. No default/shared device key. Duplicate enrollment is rejected; no implicit replacement.
- Host authentication attempt: device_id, host nonce (32 random bytes), start monotonic time, consumed flag. Ephemeral, 10-second lifetime. Device nonce independently generated by device. No persistent session or authorization granted by this host-only reference.
- Transcript: ASCII versioned domain "TAB5-AUTH-V1" followed by NUL, role ("device" or "host"), NUL, normalized ASCII device_id, NUL, raw 32-byte host nonce, raw 32-byte device nonce. HMAC-SHA256 with per-device secret. Proofs compared in constant time. Different roles prevent reflection. Host attempt consumed on first completion including invalid proof; expired attempts rejected. Firmware must independently verify host proof and consume its own challenge before allowing any authorized operation.
- Enrollment UI only prepares a credential; it does NOT load it onto a device or authenticate it. No serial changes. Key injection will require explicit trusted maintenance action, verified physical hardware identity, protected local transport and no secrets in repository/artifacts/logs. Flash encryption/secure boot and Windows storage ACLs remain release gates. SQLite secret storage in this slice is synthetic test use only; not production secure storage.
- Future KEY_PENDING -> ENROLLED only after key installation plus verified mutual handshake. No action in this slice transitions to ENROLLED or PROVISIONED. Assignment sync additionally requires authenticated operation, durable acknowledgement and replay protection.

## Acceptance
Test-mode administrator can prepare one credential for an existing planned device. Non-admin and normal mode denied; duplicate and unknown devices rejected; UI displays KEY_PENDING without exposing key. Test reference challenge with fresh nonces, wrong key/device/role, tampering, timeout and replay. No firmware reflash required for this slice. Next: physical key installation and firmware-side matching reference; do not send actual student data until security gates pass.

## Device-side portable reference
Use a fixed-size transcript buffer and injected HMAC-SHA256 provider, with no serial command or NVS key loading in this slice. Device challenge state: IDLE -> PENDING on a valid start (new independent nonce supplied by a trusted RNG adapter), PENDING -> IDLE on any completion attempt, cancellation or replacement. Expiration is 10 seconds using unsigned millisecond elapsed time (wrap-safe). Starting a new challenge invalidates the old one even if the new request is invalid. The device emits the device-role proof and verifies only the host-role proof. A successful verification is a one-shot result, not a persistent authenticated session or authorization to write. A crypto-provider failure fails closed. The production adapter must use the platform's vetted HMAC, secure RNG and protected key storage; this reference intentionally does not inject keys or change installed firmware. Cross-language vectors use public synthetic bytes, never actual credentials.

## Embedded crypto candidate
The isolated auth_compile_probe uses the documented Mbed TLS 3.x md HMAC API and public synthetic vectors to validate compatibility with the Python host. The normal learner build does not include this adapter or probe. Native compile/link and runtime self-test remain separate gates. No actual key storage or authentication transport is enabled. ESP-IDF 5.4.2 ESP32-P4 RNG documentation (https://docs.espressif.com/projects/esp-idf/en/v5.4.2/esp32p4/api-reference/system/random.html) requires main hardware entropy for guaranteed true randomness; enabling SAR ADC entropy conflicts with concurrent ADC access. Before integrating a DRBG, verify early startup ownership and availability of the pinned SDK entropy APIs; use vetted DRBG seeded with verified hardware entropy and fail closed. Do not enable ADC entropy during normal learner operation, or use fixed test vectors, bare unseeded esp_random, MAC addresses or timestamps as credentials or nonces. No radio changes. Build-only command: pio run -d firmware -e auth_compile_probe. Do not flash the probe over the working learner.

## Isolated offline nonce generator
State: NEW -> SEEDING -> READY -> EXHAUSTED/FAILED. Seed exactly once per object, at the beginning of the isolated probe setup before board peripherals are initialized. Use Mbed TLS CTR-DRBG with 48 bytes of hardware entropy and a fixed application personalization label. The entropy callback is permitted only while the startup entropy guard is active; it rejects requests at all other times. Pair bootloader_random_enable/disable around seeding. Limit output to 1024 32-byte nonces per initialization; no automatic late reseeding. Failure or exhaustion clears output and disables further generation. No copying of generator state. On production integration, review all pre-setup Arduino ADC initialization and establish exclusive entropy ownership; do not treat this probe as proof of exclusive ownership. No persistent nonce or key, no random output in serial logs. Runtime test checks unavailable-before-seed, distinct nonces, bounded exhaustion, and refusal to reinitialize; it is not a statistical or security certification. Native SDK compile and physical probe still require verification. No changes to learner environment or key provisioning.

## Authentication wire reference v1
Four ASCII newline-terminated frames: AUTH1,<normalized device_id>,<host nonce hex>; AUTH2,<device nonce hex>,<device proof hex>; AUTH3,<host proof hex>; AUTH4,<receipt proof hex>. All binary fields are exactly 64 lowercase hex characters, all frame bodies at most 136 bytes (AUTH1 with 64-character ID is 135; AUTH2 is 135). Existing HMAC transcript adds the distinct role "ack" for receipt proof; no other changes. The device only returns AUTH4 after verifying AUTH3, and host only reports mutual proof verified after validating AUTH4 against its challenge. An invalid, expired, interrupted, or replaced challenge fails closed; no unsigned success message is accepted. Host may use a new attempt after failure. No session keys, provisioning, authorization to write, key injection, or USB transport changes in this reference. Production serial integration must bound line buffering, enforce timeout while idle, discard malformed frames, pace requests, and protect credentials; current installed learner stays unchanged. Host and device use the same independent public synthetic test vectors.

## Credential record and trusted maintenance boundary
Prototype fixed 105-byte record: bytes 0..3 ASCII PLC1, byte 4 ID length (1..64), bytes 5..68 lowercase ASCII ID followed by zero padding, bytes 69..100 per-device 32-byte key (reject all-zero), bytes 101..104 IEEE CRC32 of bytes 0..100, little endian. CRC detects accidental corruption only, not tampering or authentication. Do not expose this secret-bearing record to browser, logs, Git, or unprotected artifact storage.
A portable storage service distinguishes EMPTY, VALID, CORRUPT and UNAVAILABLE. Installation accepts only an explicitly authorized maintenance call with a validated candidate; only EMPTY allows one write attempt. VALID with identical record returns ALREADY_PRESENT without writing; VALID with different record, CORRUPT or UNAVAILABLE all refuse. After a write, read back and validate the entire record. If write reports failure but readback matches, report PRESENT_AFTER_AMBIGUOUS_WRITE; if readback cannot confirm, report RECOVERY_REQUIRED without automatically retrying. No erase, replacement, or factory reset. Never treat an I/O error as missing data. No real keys in tests.
Host prepares the same byte record in memory. No export-to-file CLI or actual flash/NVS adapter in this slice. Production installer must establish trusted physical maintenance and explicit approval; enforce hardware identity, encrypted storage, access controls, protected transport, and durable readback. Current NVS partition is shared with learning journal and not encrypted on the prototype, so plaintext key installation is not a production security solution. Installed credential alone does not prove mutual authentication or change the planned assignment.
